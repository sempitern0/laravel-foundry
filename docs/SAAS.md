# SaaS / multi-tenancy development in Laravel Foundry

This is an **opt-in development blueprint**, not a complete multi-tenant SaaS implementation. Foundry does not install packages, create tenancy models, bill customers, provision tenant databases or guarantee isolation. All starters (Blade, Livewire, Svelte/Vue/React + Inertia) may use the same Laravel backend tenancy layer.

## Choosing a model

| Model | Good fit | Costs and obligations |
| --- | --- | --- |
| Shared DB / shared tables + `tenant_id` | Most early SaaS projects | Every tenant-owned query, write, export, job, cache and route must scope by tenant. Unique indexes must include tenant where applicable. A missed scope leaks data |
| Shared DB / separate schema | PostgreSQL with deliberate schema-per-tenant infrastructure | More complex connection/search path, permissions, migration and pool handling; not configured here |
| Database per tenant | Stronger logical database isolation, individual data retention requirements | Central landlord DB, tenant connection switching, provisioning, per-tenant migrations, backups, worker context, operational overhead |

The wizard offers **none**, **shared-db**, or **database-per-tenant** and records only `TENANCY_MODE` and test hostname settings. This is **not an application tenancy toggle**. A user must implement tenant resolution and enforce isolation. `TENANCY_MODE` should not be trusted as a production security control.

### Package choices to assess, not auto-install

- [stancl/tenancy](https://tenancyforlaravel.com/docs/) supports automatic tenancy bootstrapping and different storage models; **verify the installed major version** against your Laravel version and deployment/database requirements.
- [spatie/laravel-multitenancy](https://spatie.be/docs/laravel-multitenancy) offers configurable identification/switch tasks and tenant-aware queue behavior. Examine its precise model and version before adopting.
- Native Laravel approach (tenant resolver, middleware, policy, global scopes plus explicit service boundaries) suits small shared-DB apps, but demands robust adversarial tests and careful context resets.

Do not stack competing tenancy libraries or introduce tenant-aware behavior into every model automatically.

## Local subdomains, HTTPS and host resolution

When enabling SaaS mode with local HTTPS, Foundry selects `docker/caddy/Caddyfile.saas`. It adds Caddy `tls internal` for both the apex name and its wildcard subdomains. **Existing deployments must recreate Caddy after changing modes**:

```sh
docker compose --profile https up -d --force-recreate caddy-local
```

The wizard suggests `alpha.<LOCAL_DOMAIN>` and `beta.<LOCAL_DOMAIN>`, e.g. `alpha.foundry.test` and `beta.foundry.test`. The OS hosts file **does not support wildcard records**. Add individual entries for browser testing:

```text
127.0.0.1 foundry.test
127.0.0.1 alpha.foundry.test
127.0.0.1 beta.foundry.test
```

For script-only testing, the `curl --resolve` option bypasses the need to edit hosts: it directs those names to loopback while preserving the hostname in the request and TLS verification. First export Caddy's own local root certificate using `make https-setup`. Inspect it and explicitly decide whether to trust it. **Never use `-k` / `--insecure` to declare tests successful.** The wildcard certificate is generated by Caddy, not a public CA, and must be trusted by the local client. Firefox/Windows trust may be configured independently.

Apex `APP_URL` is set by Foundry's normal configurator; **your Laravel application must also decide how it recognizes tenant subdomains**. Verify cookie/session domain and `TrustHosts`/trusted proxy handling for your auth model. A single tenant hostname in the browser is not evidence of data isolation.

## Run the local smoke test

```sh
make up-wait
make tenancy-check
```

`make tenancy-check` performs a request to each configured tenant hostname through the actual local reverse proxy. It checks successful HTTP routing (and HTTPS CA validation if enabled). It intentionally performs **no seeding or writes**. For app-level tenant identification, set `TENANCY_ASSERT_HEADER=X-Tenant-Key` and implement an authenticated or safe test-only endpoint that responds with `X-Tenant-Key: alpha` on the alpha host and `X-Tenant-Key: beta` on beta. Set `TENANCY_TEST_PATH=/health/tenant` to target it.

**Do not expose a diagnostic header revealing internal tenant IDs or secrets in production.** If necessary, restrict it to `APP_ENV=local`. A successful route/header check still does not prove permission boundaries.

Configure the list with `TENANCY_TEST_TENANTS=alpha,beta`. Use separate safe fixture tenants from factories/seeders for actual isolation tests.

### Essential application feature tests (write these in the product repository)

- **Tenant A and B seed identical-looking records** with separate tenant IDs. Authenticated A requests only retrieve A's rows (list, show, search, export and count), even with an ID belonging to B.
- Attempts by A to **update/delete/attach/download** B's records return 403/404 and leave data unchanged. Test mass-assignment of a foreign `tenant_id`.
- Tenant-specific unique indexes and validation must not block a separate tenant unnecessarily; indexes must enforce invariants at the DB level.
- Host-to-tenant resolution rejects unknown, suspended and mismatched hosts. Test central administrative routes separately and avoid relying on incoming client headers as trustworthy tenant identity.
- Queue jobs, scheduled tasks, events, notifications, cache prefixes and file/object storage must keep or reconstruct the correct tenant context and **clear it after each job/request**. Exercise A → B → A sequentially in the same worker process.
- API keys, webhooks, signed URLs, authentication sessions, rate limits, billing owner checks, audit trails and cross-tenant relationships are isolated and enforce authorization on the server.
- For database-per-tenant: verify provisioning, per-tenant migration, teardown, rollback/recovery, landlord DB queries, tenant DB permissions and restored-backup behavior with at least two distinct databases.
- Test across the project's **actual** DB engine (PostgreSQL/MySQL/MariaDB/SQLite) rather than relying only on SQLite in-memory when production uses other SQL semantics.
- Run tests with correct model factories, `RefreshDatabase` or isolated test databases; never point tenant tests at live data or production service credentials.

## Local SaaS add-ons that require explicit product decisions

1. **Onboarding**: registration, invitations, teams, roles/policies, tenant ownership and custom domain verification.
2. **Subscriptions**: Cashier Stripe, Spark or a chosen payment provider. Use sandbox webhooks and test clocks, never real charges in local tests.
3. **Email**: Mailpit for welcome/invite/verification flows; no real deliveries during tests.
4. **Queues**: Redis/database driver and worker tests for tenant context; retry/idempotency under worker reuse.
5. **Storage**: tenant-aware disk keys/object prefixes, private file URLs and lifecycle/retention rules.
6. **Background jobs and scheduling**: dispatch per tenant, idempotency, quotas and eventual consistency.
7. **Monitoring**: aggregate health without leaking tenant data; logs should use stable internal correlation IDs rather than sensitive records.
8. **Production deployment**: stage the same release and test identity, domains, DB engine, schema migrations, jobs and file storage using [DEPLOYMENT.md](DEPLOYMENT.md).

## Running against staged production-like containers

Foundry's production Compose is a reference **single PostgreSQL service** and does not automatically support database-per-tenant provisioning, wildcard public DNS or multiple tenants. For a real SaaS product, adapt this deployment explicitly: compatible migrations, tenant provisioning, database credentials/permissions, queues/cache, storage, TLS and routing. Do not claim parity until a release-image smoke test in staging passes.

**Current scope:** optional interactive mode, wildcard local Caddy config, and connectivity smoke tests. No hidden dependency installation, domain DNS change, schema modification, or database deletion.
